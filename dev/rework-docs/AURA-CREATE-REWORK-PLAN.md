# SkuAuras: rework of the "create a new aura" flow

Date: 2026-08-23. Status: **BUILT 2026-08-23 under v43.1, UNTESTED in game.**
The plan below is left as written; section 8 at the end records what was
actually built, where it deviated and why, and what to test first. Read section
8 before acting on anything above it.

Everything marked **measured** was counted out of the shipped source or out of
the live account's SavedVariables. Everything marked **estimate** is a guess.
Do not act on an estimate as if it were a measurement.

## 0. Verdict

Three changes, in this order. Each one stands on its own and can ship alone.

1. **The draft stops living in the menu path.** Today an aura *is* the path the
   user walked; that single fact causes every symptom (unbounded depth, no
   review, no removal, ENTER commits anywhere). A draft table plus a flat
   workbench removes all of them at once.
2. **`ifNot` leaves the creation menu.** It is expressible, unused, and already
   half-broken. Details and evidence in section 4.
3. **Lists become toggles.** The data model has supported OR-ed multi-value
   conditions since forever; the menu never exposed it. One new framework flag
   (`toggleInPlace`) makes every list in the addon capable of it.

## 1. What the flow is today

`Sku/SkuAuras/Options.lua`, `SkuAuras:MenuBuilder` -> "Neue aura".

The aura is encoded as a **menu path**:

    type -> attribute -> operator -> value -> attribute -> operator -> value
         -> "aktion" -> "dann" -> action -> output -> output -> ...

`NewAuraAttributeBuilder` / `NewAuraOperatorBuilder` / `NewAuraValueBuilder` /
`NewAuraOutputBuilder` each build the *next* level and re-point
`self.BuildChildren` to the next builder in the chain. `OnAction` on the type
node (the select target) walks `collectValuesFrom` back up the `.parent` chain
and reconstructs the aura from the node `internalName`s.

**Measured** consequences:

- A three-condition aura with two outputs is **14 menu levels** deep.
- ENTER at *any* level commits the aura as built so far. That is the "confirming
  one step sends me back" the request names.
- Nothing can be reviewed or removed while building. Each level only *excludes*
  what has already been used (`usedAttributes`, `usedOutputs`,
  `RebuildUsedOutputsHelper`); there is no list of what is in the draft.
- Multi-value (OR) conditions are unreachable from this menu, although the
  storage format and the evaluator both support them and the user already has
  six of them (section 4.3).
- The "Bearbeiten" path on an existing aura (`BuildManageSubMenu`) already has
  the right *shape* - Bedingungen / Ausgaben as separate sections - but each
  section still uses the same chained builder, and every ENTER calls
  `SkuAuras:UpdateAura`, which deletes and re-adds the whole aura, re-derives
  its name and navigates away. Same defect, one level up.

## 2. Target structure

### 2.1 "Neue Aura" gets two children

    Neue Aura
      +- Basis-Auren           (recipes; spell name + aura name, then done)
      +- Eigene Aura erstellen (the workbench)

### 2.2 The draft

    SkuAuras.draft = {
       type = "if",          -- fixed, see section 4
       attributes = {},      -- [attName] = { {op, value}, {op, value}, ... }
       actions = {},
       outputs = {},
       name = nil,           -- nil -> auto-generated by BuildAuraName
    }

One table, per session, not persisted. It is the *only* thing the workbench
reads and writes. The menu tree becomes a view onto it, which is what makes
order-independence, review and removal fall out for free.

### 2.3 The workbench

    Eigene Aura erstellen
      +- Bedingungen  (<n>)          -> list of current conditions
      |    +- <attribute> <op> <value>   -> Ändern / Löschen
      |    +- Bedingung hinzufügen       -> attribute -> operator -> value(s)
      +- Aktion: <current>           -> single-select, ENTER sets and stays
      +- Ausgaben (<n>)              -> TOGGLE list, ENTER toggles, stays
      +- Name: <auto|custom>         -> free text, empty = auto
      +- Aura erstellen              -> speaks the assembled aura, then creates
      +- Verwerfen                   -> clears the draft

Rules:

- The workbench level itself is **never** a select level. Only "Aura erstellen"
  and "Verwerfen" commit anything.
- Every section is enterable in any order, any number of times.
- Each section's own node name carries its state (`Ausgaben (2)`,
  `Aktion: audio ausgabe einmal`), so arrowing across the workbench reads the
  whole draft back without entering anything.
- Leaving the workbench with arrow-left does **not** discard the draft; it is
  still there on re-entry. "Verwerfen" is the explicit clear.

### 2.4 The condition sub-flow

"Bedingung hinzufügen" is the only place that is still a chain, and it is
bounded at three levels:

    attribute -> operator -> value list (TOGGLE)

The value list is a toggle list, because one attribute may hold several OR-ed
values. Arrow-left from the value list writes the toggled set into the draft as
one condition group and lands back on the condition list. No commit.

Semantic detail worth getting right: the evaluator ORs the entries of one
attribute group unconditionally. For affirmative operators that is what the user
means ("Eisbarriere *or* Manaschild removed"). For `containsNot` it also reads
correctly ("any of these buffs missing"). For `isNot` on a CATEGORY attribute an
OR of negations is always true - a footgun the toggle list would newly expose.
Either restrict the toggle list to a single value when the chosen operator is
`isNot`, or evaluate negating groups with AND. **Measured:** no stored aura in
the live account uses a negating operator at all, so either choice is a
free change today.

### 2.5 The editor of an existing aura is the same code

"Auren verwalten" -> "Bearbeiten" loads the stored aura into the draft, opens
the same workbench, and its commit button writes back under the old name
instead of creating. One editor, two entry points. This deletes the whole
`UpdateAura`-per-keystroke path.

## 3. Base auras (the "Basis-Auren" submenu)

A recipe is a table: a fixed condition/action/output skeleton plus a list of
typed prompts. **Estimate:** ~60 lines of data for ten recipes.

    { id = "buffLost",
      friendlyName = L["Eigener Buff verloren"],
      prompts = { {kind = "spellName", into = "spellName"} },
      build = function(p) return {
         attributes = {
            event        = { {"is", "SPELL_AURA_REMOVED"} },
            sourceUnitId = { {"contains", "player"} },
            spellName    = { {"is", p.spellName} },
         },
         actions = { "notifyAudioSingle" },
         outputs = { "output:sound-glass1" },
      } end },

`kind` is one of `spellName` (reuse the existing spell-name/spell-ID resolution
in `tPromptForSpellId` + `SkuAuras:SpellGroupName`), `number`, or nothing.

Proposed catalogue. The first two are **measured** - they are literally two of
the auras in the live account ("eisbarriere cd", "schild gebrochen"), which is
the evidence that the recipe shape is right:

1. Eigener Cooldown wieder bereit   - spell name
2. Eigener Buff verloren            - spell name
3. Buff fehlt mir                   - spell name          (the ex-`ifNot` case)
4. Debuff auf mir                   - spell name
5. Buff auf mir läuft aus           - spell name + seconds
6. Debuff auf Ziel läuft aus        - spell name + seconds
7. Ziel wirkt Zauber                - spell name
8. Eigene Gesundheit unter N%       - percent
9. Ziel unter N%                    - percent
10. Waffenverzauberung läuft aus    - seconds

After the prompts the recipe asks for an aura name (default: the recipe name
plus the spell name) and creates the aura with `customName = true`. One confirm,
no builder.

## 4. `ifNot`: remove it from the creation menu

### 4.1 What it does

`Sku/SkuAuras/Core.lua:2866`. `if` fires when every condition is true. `ifNot`
fires when `tOverallResult == false`, i.e. when **at least one** condition is
false. So `ifNot(A and B)` is `not A or not B` - a disjunction of negations.

### 4.2 It is expressible without the type

- **One condition.** `ifNot(A)` is `if(not A)`, and every attribute type has a
  negating operator (`SkuAuras.operatorsForAttributeType`, data.lua:2405):
  CATEGORY `isNot`, SET `containsNot`, BINARY has two values so `is <other>`
  covers it, ORDINAL `isNot` / `bigger` / `smaller`.
  The one gap: `not (x bigger N)` is `x <= N`, which needs two OR-ed entries
  (`smaller N` or `is N`) because there is no `biggerOrEqual`. See 4.5.
- **Several conditions.** Not expressible in one `if` aura directly - different
  attributes are AND-ed. It *is* expressible by composition: a custom-named aura
  becomes a BINARY attribute `skuAura<Name>` with values `true`/`false`
  (`SkuAuras:UpdateAttributesListWithCurrentAuras`, Core.lua:1224). Build the
  positive aura "A and B" with action `nothing`, then write
  `if (skuAura<Name> is false)`. Exact equivalent, one firing.

### 4.3 Nobody uses it

**Measured**, 2026-08-23:

- Live account (`_anniversary_` SavedVariables, largest `Auras` block):
  22 auras, **0** of type `ifNot`; operators used: `is` 49x, `contains` 23x,
  `isNot` / `containsNot` / `bigger` / `smaller` **0x**. Six attribute groups
  already carry more than one OR-ed value.
- Shipped default sets (`Sku/SkuAuras/defaultAuras.lua`): 19 auras, all `if`,
  **0** `ifNot`.

### 4.4 It is already degraded

Not a style objection - three concrete defects that only affect `ifNot`:

- **Outputs can be empty.** The evaluation loop `break`s on the first false
  condition. For `ifNot` that break *is* the fire path, so the five
  output-feeding assignments after it (`buffListTarget`, `debuffListTarget`,
  `spellNameOnCd`, `weaponEnchantMainHandSelected`,
  `weaponEnchantOffHandSelected`) never run for any attribute past the break.
  An `ifNot` aura that announces a buff name can announce nothing.
- **The v43.0 event pre-filter assumes affirmative semantics.**
  `tAuraWatchesEvent` (Core.lua:1967) argues in its own comment that an
  `isNot` event condition "cannot fire on that event anyway". True for `if`,
  inverted for `ifNot`: a failed event condition is exactly what makes an
  `ifNot` aura fire. Currently only the synthetic `SPELL_COOLDOWN_START` pass
  passes `aRequiredEventValue`, so the damage is narrow - but the assumption is
  already in the code and will spread.
- **No once-gate bookkeeping.** The whole re-arm apparatus
  (`tHasCountCondition_*`, the deadline scheduler, `tSmallerDurationNoRead`)
  lives in the `if` branch only. `ifNot`'s else-branch is a bare
  `tAuraData.used = false`.

Plus the practical point: an `ifNot` aura carrying an event condition fires on
essentially every combat-log event that is *not* the named one. That is a
firehose, and it is presumably why nobody has one.

### 4.5 Decision

- Remove `ifNot` from the **creation menu**. `SkuAuras.Types` loses its menu
  role entirely; the workbench hard-codes `type = "if"`, and the type step
  disappears from the flow.
- **Keep the `ifNot` branch in the evaluator.** It costs nothing for auras that
  are not `ifNot` and it keeps any imported or shared legacy aura working. Zero
  risk, ~40 lines left in place. Mark it legacy-read-only in a comment.
- "Auren verwalten" still shows a legacy `ifNot` aura and lets it be disabled or
  deleted; "Bearbeiten" on one converts it to `if` only on explicit
  confirmation, otherwise it stays read-only.
- Optional, and independent: add `biggerOrEqual` / `smallerOrEqual` to
  `SkuAuras.Operators` and to the ORDINAL subset. It closes the one real
  expressiveness gap in 4.2 and costs about 20 lines.

## 5. The `toggleInPlace` framework flag

`Sku/SkuZOptions/templates.lua`, `OnPostSelect`.

Today ENTER on a leaf either dispatches to the level's select target and parks
the cursor on that target, or - in the generic branch - runs the leaf's own
`OnAction` and then moves the cursor to `self.parent`. Neither stays put, so a
toggle list is not currently buildable.

New: a node with `toggleInPlace == true` gets a branch **before** the
selectTarget branch (ENTER inside a select level always dispatches to the
level's select target, so the toggle check has to come first):

1. call `self:OnAction(self, tCleanValue, self.parent.name)`
2. do **not** clear `self.children`
3. leave `SkuOptions.currentMenuPosition = self`

The node re-speaks itself through the existing `OnEnter` at the end of
`OnPostSelect`, so the user hears the new state of the item they just toggled
and the cursor has not moved. The node's own `OnAction` updates its `name`
(prefix `L["ein"]` / `L["aus"]`, or the existing `L["Selected"]..";"`
convention).

Users of the flag in this rework: the output list, every condition value list,
and (later, for free) any other multi-select list in the addon.

`isMultiselect` already exists in the template but is a half-feature - it
concatenates names into the target's name with `;` separators and has hardcoded
`Small`/`Large` exceptions, and **measured**: no node in the tree sets it. Leave
it alone, do not build on it.

## 6. Regression net

Per the project rule that every regression fix adds its invariant to
`/skucheck`:

- `/skucheck auras`: the creation menu can no longer produce `type == "ifNot"`;
  the draft table is empty whenever the menu is closed.
- `/skucheck menu`: a node with `toggleInPlace == true` must have its own
  `OnAction` (otherwise ENTER silently does nothing - same class as the existing
  selectTarget-miss tripwire).
- The existing aura tree sweep stays as is.

1. `toggleInPlace` in templates.lua + the `/skucheck` tripwire. Testable on its

2. Draft table + workbench + condition sub-flow. Behind the new "Eigene Aura
   erstellen" entry, with the old "Neue aura" chain still reachable during the

3. Base auras.
4. Point the "Bearbeiten" path at the same workbench; delete the old chain and

**Estimate:** step 1 is small; steps 2 and 4 are the bulk; step 3 is data.

## 8. What was actually built (2026-08-23, v43.1) — UNTESTED in game

All five steps of section 7 landed in one pass, on request. Files touched:
`SkuZOptions/templates.lua`, `SkuZOptions/SkuMenu.lua`, `SkuAuras/Options.lua`
(the whole builder section rewritten), `SkuAuras/data.lua` and
`SkuAuras/Core.lua` (comments only), `SkuCore/LocalMenu.lua` (`/skucheck`),
plus 24 new keys in each of the three locale files.

### 8.1 Deviations from the plan

- **The flag is `actionInPlace`, not `toggleInPlace`.** It turned out to be
  needed for the text prompts ("Zauber", "Name") just as much as for the
  toggles: both want "run my own OnAction and leave the cursor here". The name
  follows what it does.
- **It is load-bearing beyond multi-select.** In the EDIT path the workbench
  sits under "Auren verwalten", which is `isSelect`, and `selectTarget`
  cascades down every rebuilt level. Without a branch that runs BEFORE the
  selectTarget branch, every action leaf in the workbench would have dispatched
  to the manage menu's `OnAction` instead of its own — and its "Löschen" entry
  would have collided by NAME with the manage menu's own "Löschen". Every
  action leaf in the workbench therefore carries the flag, not just the toggles.
- **Four recipes, not ten.** Named by the user; they are the common ones:
  1. `targetAuraLost` — source self, event aura removed, dest your target, spell
  2. `ownCooldownReady` — source self, event cooldown end, spell
  3. `ownAuraLostSpoken` — source self, event aura removed, spell, output = spell name
  4. `newTargetOwnDebuff` — own-cast lists only, event target change, debuff list target contains spell
  Each form is Zauber / Ton / Name / Aura erstellen. Only "Zauber" is
  mandatory; the sound and the name have defaults, and recipe 3 defaults to no
  sound because it announces the spell name instead.
- **Typing a spell NAME works, not just an ID.** `tResolveSpellText` resolves,
  in order: the enUS group key as typed, the localized-name→group map, then a
  case-insensitive sweep of the attribute's own value list (matching `speakName`
  or the tag-stripped key). A numeric input still goes down the existing ID
  lane. Everything resolves to the value KEY the attribute stores, so a typed
  name and a picked list entry produce byte-identical auras.
- **The `isNot`-OR footgun of section 2.4 was NOT addressed.** The evaluator
  still ORs a group unconditionally. Left as it was on purpose: changing
  evaluation semantics is a separate, testable change, and measured today no
  stored aura uses a negating operator at all.
- **Empty conditions never reach the draft.** `tDraftSyncCondition` attaches a
  condition row only while it holds at least one value, so walking
  attribute→operator→values and arrowing straight back out leaves nothing
  behind. That invariant is now a `/skucheck` tripwire.
- **`biggerOrEqual` / `smallerOrEqual` were NOT added.** Still the one real
  expressiveness gap; see 4.2. Cheap to add later.

### 8.2 Deleted

`SkuAuras:BuildAuraTooltip` (path-walking; replaced by
`SkuAuras:BuildStoredAuraTooltip`, which reads the stored aura),
`RebuildUsedOutputsHelper`, `NewAuraAttributeBuilder`, `NewAuraOutputBuilder`,
`NewAuraOperatorBuilder`, `NewAuraValueBuilder`, `SkuAuras:UpdateAura`, the old
"Bedingungen"/"Ausgaben" edit sub-chains, and the two dead helpers
`NoIndexTableGetn` / `RemoveTagFromValue`. `SkuAuras:CreateAura` in Core.lua is
left in place but no longer called from the menu.

### 8.3 New `/skucheck` tripwires

- `menu`: `tMenuActionInPlaceMisses` — an ENTER on an `actionInPlace` node that
  has no OnAction of its own. Unlike the selectTarget miss, that key press does
  nothing whatsoever, not even the step up to the parent.
- `auras`: stored `ifNot` auras are counted as PENDING (legacy/imported; the
  builder cannot make one). A number that GROWS between sessions means the type
  came back in through some path.
- `auras`: a draft condition row attached with no values — `tDraftSyncCondition`
  was bypassed, and such a row is silently dropped on save.

### 8.4 What to test first, in this order

1. **The toggle itself.** "Neue Aura" → "Eigene Aura erstellen" → "Ausgaben" →
   ENTER on an entry. Expected: the entry speaks itself again with "ein" after
   the name, the cursor has NOT moved, and pressing ENTER again says "aus". The
   sound entries must still audition on focus (that is the `auraOutputKey`
   patch in templates.lua).
2. **One condition, several values.** Bedingungen → Bedingung hinzufügen →
   "zauber name" → "gleich" → toggle two spells on → arrow left twice.
   Expected: "Bedingungen (1)" and the row reads
   "zauber name;gleich;A;oder;B;". This is what the old menu could not do at all.
3. **Typing a name.** In any spell value list, "Zauber eingeben", type a
   localized spell name. Expected: "Wert gesetzt: <name>" and the cursor back on
   the input entry. Then try an ID, then try nonsense (expect
   "Unbekannter Zauber", nothing changed).
4. **Create.** Set an action and at least one output, then "Aura erstellen".
   Expected: "Aura erstellt" followed by the level name; the aura is in "Auren
   verwalten". Try it once with a custom name and once with the auto name.
5. **Base auras.** One of each of the four. Check the created aura in "Auren
   verwalten" reads the way the recipe describes.
6. **Edit.** "Auren verwalten" → an aura → "Bearbeiten". Expected: the workbench
   opens PRE-FILLED, changing something and pressing "Aura speichern" says
   "Aura gespeichert", and no aura was duplicated. Check especially a rename.
7. **`/skucheck auras` and `/skucheck menu`** after all of the above: no new
   VIOLATION lines.

## 9. First in-game pass (2026-08-23) — one load-time defect, one semantics fix

### 9.1 The addon did not load at all

BugGrabber, session 1479:

    Interface/AddOns/Sku/SkuAuras/Options.lua:381: unfinished string near '":'
    Interface/AddOns/Sku/SkuZOptions/SkuMenu.lua:309: attempt to call a nil value

One root cause, two errors. Six string literals in `SkuAuras:BuildStoredAuraTooltip`
had a RAW newline where `\r\n` belonged — a bash heredoc ate the backslashes
while that function was being inserted. A load-time syntax error means the whole
file is refused, so `SkuAuras:MenuBuilder` was nil, which is what
`SkuMenu.lua:309` then tried to call when the aura menu opened.

**The gate that let it through:** `luaparser` — the pre-reload syntax check this
project uses — does **not** reject a raw newline inside a `"..."` literal. The
WoW client does. So the check said OK on a file the client would not load.

New second gate, to be run after the luaparser check from now on:

    py -3 dev/rework-docs/_lua_string_lint.py Sku

It flags unterminated single-line string literals (long strings and block
comments are skipped) and exits 1 on any finding. The whole 185-file tree is
clean after the fix.

### 9.2 The `isNot`-OR footgun (section 2.4) is fixed

The several values of ONE condition are now a **set**, and the operator applies
to the set — De Morgan:

- affirmative operator: holds when the attribute matches **any** of them
  ("zauber name gleich Eisbarriere ODER Manaschild")
- negating operator: holds only when it matches **none** of them
  ("zauber name ungleich Frostblitz UND Feuerball")

Before, the group was OR-ed unconditionally, which made a negating group a
tautology on a scalar attribute: a class cannot be both warrior and mage, so
"class isNot warrior OR class isNot mage" was true for every class. The
multi-select value lists of this rework are exactly what makes such a group easy
to author, which is why the reading had to be pinned down now.

Three places had to agree, and do:

- `SkuAuras/Core.lua`, the `#tAttributeValue > 1` branch of the evaluate loop.
- `SkuAuras:BuildAuraName` — the aura's own name.
- `tConditionText` — the condition row in the builder.

The joining word is the reading: "oder" for an affirmative group, "und" for a
negating one. That is deliberate and it is the point — a blind user cannot see a
truth table, so the difference has to be in what the entry says.
`SkuAuras.negatingOperators` (data.lua) is the single source both sides read.

Two things fell out of the same edit:

- The group's threshold tally is now taken **once per condition**, matching the
  census and the single-value branch. It used to be incremented once per
  matching VALUE, so a two-value group that matched twice counted as two
  conditions and could push the once-gate formula past its own total.
- The value loop now breaks as soon as the answer is decided instead of
  evaluating every value.

**Measured 2026-08-23:** no stored aura in the live account uses a negating
operator at all (`is` 49x, `contains` 23x, `isNot`/`containsNot` 0x), and none of
the 19 shipped set auras does either. Nothing that exists changes meaning.

New `/skucheck auras` tripwire: a stored condition group that MIXES operators.
The group's reading is taken from entry 1, so a mixed group's name promises
something the evaluation does not do. The builder cannot create one; a
hand-edited SavedVariables file can. Reported as pending, not as a violation.

### 9.3 Still open

`biggerOrEqual` / `smallerOrEqual` (section 4.2). Unchanged, not built.

## 10. Duration attributes get their own operator set (2026-08-23)

A remaining duration is a **continuously falling** reading, sampled on events.
`gleich 8` on it is a condition that can never be true, and `ungleich 8` one
that is never false — the first makes an aura silently dead, the second makes it
silently unconditional. Both look correct in the menu, which is what makes them
worse than a missing operator.

New attribute type, alongside CATEGORY / BINARY / ORDINAL / SET:

    THRESHOLD = operatorsSubset("bigger", "smaller"),

Applied to the six duration attributes: `buffListTargetDuration`,
`debuffListTargetDuration`, `buffListPlayerDuration`,
`debuffListPlayerDuration`, `weaponEnchantMainHandDuration`,
`weaponEnchantOffHandDuration`. Everything else that is numeric — health,
resource, combo points, item count, stacks — stays ORDINAL and keeps all four
operators, because those ARE sampled at exact values.

**Not** applied to `targetUnitDistance`, although it has the same continuous
shape. LibRangeCheck returns bucket boundaries rather than a free float, so
`gleich 30` there may well be meaningful. Left as ORDINAL deliberately; revisit
only with a measurement of what the checker actually returns.

Only two places in the codebase read an attribute's `type` (the operator-subset
lookup and the numeric sort of a value list), and both were updated — the sort
now treats THRESHOLD numerically too, or the list would read 1, 10, 100, 11.

Stored auras are untouched: `is`/`isNot` still exist and still evaluate, they
are only gone from the builder — the same shape as the `ifNot` removal.
**Measured 2026-08-23:** the active profile has no duration condition at all,
and none of the 19 shipped set auras has one, so nothing in the field is
affected.

New `/skucheck auras` tripwire: a stored THRESHOLD condition using `is` or
`isNot`, reported as pending. That is the machine-checkable shape of "this aura
cannot fire" / "this condition is not a condition".

### Explicitly declined

`biggerOrEqual` / `smallerOrEqual` — the user's call, 2026-08-23: the values are
close enough together that an off-by-one step does not matter in practice. Do
not re-propose it.

## 11. Second pass (2026-08-23) — naming, one level less, the read-back

### 11.1 "Ereignis Quelle/Ziel" reads better the other way round

deDE only:

    L["Quelle (L)"] = "Quelle des Ereignisses (L)"
    L["ziel (L)"]   = "Ziel des Ereignisses (L)"

enUS ("Event source (L)" / "Event target (L)") and frFR ("Source de
l'événement (L)") were already idiomatic and are untouched — the complaint was
about the German compound, not about the meaning.

### 11.2 "Bedingung hinzufügen" is gone as a level

The attribute list now sits **directly** in `Bedingungen (n)`, behind the
existing condition rows. The step carried no information: exactly one thing was
behind it, so it was a keypress that only ever said "yes, really". The two kinds
of entry are told apart by what they SAY — a row reads
"attribut;operator;wert", a bare attribute reads its name alone.

### 11.3 The base auras are named after what they DO

Five recipes now, named in the order the user thinks about them rather than in
the order the conditions are wired:

1. **Dein Debuff auf Ziel läuft aus** — source self, aura removed, dest target,
   `auraType is DEBUFF`, spell
2. **Dein Buff auf Ziel läuft aus** — the mirror, `auraType is BUFF`
3. **Eigener Cooldown wieder bereit** — unchanged
4. **Buff auf Gruppenmitglied ausgelaufen** — source self, aura removed,
   `destUnitId contains party`, `auraType is BUFF`, spell; outputs are FIXED at
   sound + `output:spellName` + `output:destUnitId`
5. **Debuff bei Zielwechsel ausgeben** — own-cast lists only, target change,
   debuff list target contains spell

The `auraType` condition is what makes 1 and 2 two recipes instead of one label
with a coin flip behind it. It is populated from CLEU arg 15
(`tEvaluateData.auraType`, Core.lua) and is exact for `SPELL_AURA_REMOVED`.

Recipe 4 is modelled on the user's own `SEELENSTÄRKE` aura — source self, aura
removed, `spellgroup:Power Word: Fortitude`, outputs `sound-error_dang` +
spell name + dest unit — plus the group condition it was missing. Without
`destUnitId contains party` the same aura also fires for a buff dropping off a
stranger you happened to have buffed. `party` **includes** the player (see the
destUnitId evaluate), which is what you want: your own Fortitude dropping is
news too. Its two data outputs are fixed rather than optional, because "which
buff, on whom" is the entire point and a beep alone says neither.

**Assumption flagged:** "target number condition" was read as `destUnitId` — as
a condition (`contains party`, so the aura is about the group) *and* as the
`output:destUnitId` announcement that names the unit. If only one of the two was
meant, the other is a one-line change in the recipe table.

### 11.4 The read-back is back, everywhere

The old chained builder rewrote the reading frame at EVERY step, so wherever the
user stood they could read the aura as it was so far. That is the one thing the
path-as-aura design got right, and losing it was a regression.

`tSetDraftTooltip(aNode, aOwnText)` now runs from the `OnEnter` of **every**
node in the builder — workbench entries, condition rows, the three entries under
a row, attribute nodes, operator nodes, every value toggle, every output toggle,
every action entry. `aOwnText` is what that entry itself is (an attribute's or
action's tooltip, or the condition the level belongs to) and becomes the first
section, so the frame reads "what you are standing on, then the whole aura" —
the same shape the old `SkuAuras:BuildAuraTooltip` produced.

Two nodes must call `SkuGenericMenuItem.OnEnter` first rather than replace it:
the aura-output toggles and the recipe sound list. That generic handler is what
AUDITIONS the beep; overriding it outright would have silenced the preview.

The base-aura forms got the equivalent (`tBaseFormSummary`): the recipe's own
skeleton rendered through the same condition formatting, so a recipe is not a
black box just because it fills itself in. With no spell picked yet the spell
slot renders as "nicht festgelegt" — that key is not in `SkuAuras.values`, so
`tValueName` falls through to the raw string.

## 12. Third pass (2026-08-23) — the separator, the naming, the pick list

### 12.1 ":" is not a separator in this addon, ";" is

`SkuVoice-1.0.lua`, the sanitiser around line 520, is the authority on this and
it settles three complaints at once:

- **`";"` is THE separator.** It is what the voice layer splits parts on, which
  is why every aura name in this project is `";"`-joined.
- **`":"` is NOT converted** — that gsub is commented out. So every "label: value"
  entry the builder produced ("Aktion: audio ausgabe einmal", "Ton: ...",
  "Name: ...", "Zauber: ...") was spoken as one run-on blob. Only one was
  reported; all of them had it. All of them now use `";"`.
- **`"/"` IS converted to `L[";slash;"]`.** That is exactly why the buff/debuff
  attribute was heard as "buff **slash** debuff". Its label is now
  "Buff oder Debuff" / "Buff or debuff" / "Amélioration ou affaiblissement" —
  the KEY `L["buff/debuff"]` is unchanged, only the three values.

The reading-frame section headers keep their colons: they are prose, and a
`\r\n` follows each one, which the sanitiser turns into a separator anyway.

### 12.2 "Aktion" was the wrong word

The entry picks *how* something is announced — audio, chat, audio once. That is
an output TYPE, not an action, and "Ausgaben" already existed next to it.

    Ausgabe Typ;audio ausgabe einmal     (was "Aktion: audio ausgabe einmal")
    Ausgabe (2)                          (was "Ausgaben (2)")

The stored field is still `actions`; this is naming only.

### 12.3 The base-aura "Zauber" entry offers the real list

It was type-only, which made the recipes *harder* to use than the builder they
are supposed to be the easy path to. Now RIGHT opens the attribute's own value
list — the same entries, in the same order, through the same sorter
(`tSortedAttributeValues`, factored out of `tBuildValueToggleList`) — and ENTER
still types a name or an id.

Both ways live on ONE entry through the flag pairing documented on the template:
`actionOnEnter` + `actionInPlace`, because with children present ENTER would
otherwise descend. `isSelect` makes the entry the target its own children
dispatch to, so a single `OnAction` serves both paths and tells them apart by
whether the node it was handed is itself.

`tBuildValuePickList` is the single-pick counterpart of the toggle list: a
recipe takes exactly one spell, so there is no on/off state to carry. Same
attribute, same sorter — picking "Frostbolt" here and picking it in the custom
builder produce the same stored value.

### 12.4 auraType (buff/debuff) is out of the recipes, kept as an attribute

**It works.** `tEvaluateData.auraType = tEventData[15]`, guarded by
`sfind(subevent, "_AURA_")` (Core.lua), so it is set only for aura subevents and
arg 15 is genuinely `auraType` for those. Not broken — just misplaced.

It was dropped from all three recipes that had it. The spell name already
decides whether an aura is a buff or a debuff, so next to a named spell the
condition can only be redundant — or, if the user picks the recipe whose label
does not match their spell, fatal and silently so. Same rule as the duration
`gleich` in section 10: a condition that is redundant when right and invisible
when wrong does not earn its place.

The consequence is that "Dein Debuff auf Ziel läuft aus" and "Dein Buff auf
Ziel läuft aus" now build identical conditions and differ only in the aura NAME
they generate. That is fine and deliberate — the label is how the user finds the
recipe, and the generated name is what gets read back in "Auren verwalten".

The attribute itself stays. It is the only way to express a **spell-agnostic**
aura: "any debuff was applied to me" (`event is SPELL_AURA_APPLIED` +
`destUnitId contains player` + `Buff oder Debuff is DEBUFF`, no spell name).
Nothing else in the attribute set can say that.

## 13. "Why did my aura not fire?" — /skuauratrace (2026-08-23)

The evaluate loop BREAKS on the first false condition and says nothing about it.
That is right for the hot path — hundreds of combat-log events a second, every
stored aura evaluated against each — and useless the moment one specific aura
stays silent and the user cannot see which condition refused.

    /skuauratrace <part of the aura name>     -- start
    /skuauratrace off                         -- stop

Scoping to ONE aura by a case-insensitive substring is what makes it affordable.
An unconditional trace would write a line per aura per event and flush the whole
12000-line ring inside a second — even behind the verbose gate, because
`dprintv`'s arguments are still built by the caller. With a name filter the idle
cost is one `sfind` on a string already in hand, and only while a trace is set.

Each condition logs the stored condition AND the live value it was compared
against, because "spellName is Mark of the Wild -> false" alone does not say
whether the event carried a different spell or no spell at all:

    auratrace <name>: sourceUnitId contains player -> false   (live: {party2})
    auratrace VERDICT <name>: event SPELL_AURA_REMOVED  allConditionsTrue false ...

Read it back with

    py -3 dev/rework-docs/_dbgtail.py 200 auratrace

**The last condition line before the VERDICT is the culprit** — the loop breaks
there, so conditions after it were never evaluated and do not appear. That is
deliberate: tracing must not change the control flow, because the threshold
tallies the once-gate re-arm reads are built inside that same loop.

### 13.1 The recipe that prompted it

"Buff auf Gruppenmitglied ausgelaufen" was renamed to **"Dein Buff auf
Gruppenmitglied ausgelaufen"**. It carries `sourceUnitId contains player`, i.e.
it only fires for a buff *the player cast* — modelled on the user's own
`SEELENSTÄRKE` and `arkane intelligenz` auras, which both have that condition
for good reason (a priest wants to know when THEIR Fortitude drops, not when a
stranger's does). The old label promised something broader than what it built.

If a "any buff on a group member, whoever cast it" variant is wanted later, that
is the same recipe minus the `sourceUnitId` line — a deliberate second recipe,
not a change to this one.

## 14. Base auras reuse the condition value list (2026-08-23)

The recipe's spell entry had a value list **of its own** (`tBuildValuePickList`):
one pick, then the cursor was thrown back out, and "Zauber eingeben" sat on the
parent as an ENTER action instead of at index 0 of the list. So the easy path
behaved differently from the real builder for no reason. Deleted; the recipe
form now opens the SAME `tBuildValueToggleList` the custom builder opens —
same entries, same order, same multi-select, same "Zauber eingeben" first.

Several values per recipe come for free with that: "Mondfeuer **oder**
Insektenschwarm" is one aura.

### 14.1 What had to change to share it

A recipe is DATA now, not a build function:

    fixed     - the conditions the recipe pins down itself
    attribute - the one the user fills in
    operator  - how that attribute is compared

so the filled-in attribute is an ordinary condition group
(`{att, op, values}`) and can be handed straight to the shared list.

`tBuildValueToggleList(aLevel, aCond, aOwnerNode, aCtx)` grew one optional
context argument, because the list previously assumed it was always editing
**the draft**:

- `onChange(aCond)` replaces `tDraftSyncCondition` — a recipe's condition must
  NOT be attached to `SkuAuras.draft.conditions`.
- `ownerLabel(aCond)` replaces the owning row's `tConditionText` label.
- `tooltip(aNode)` replaces the draft read-back with the recipe read-back.

All three default to the draft behaviour, so the custom builder passes nothing
and is untouched. `tPromptForSpellValue` takes the same context, so typing a
name updates the recipe's label exactly like toggling one does.

### 14.2 Why the "Mal der Wildnis" aura never fired

**It was never created.** Measured: zero occurrences of "Wildnis" or
"Gruppenmitglied" anywhere in the live SavedVariables, across all five stored
`Auras` blocks, after a reload — and zero `auratrace` lines, because the trace
was never armed either.

Worth recording as a diagnosis pattern: before reasoning about why an aura does
not fire, confirm the aura EXISTS in the store. Two hypotheses (a druid buff
having a non-player source; the group-identity lane failing to resolve) were
argued at length against an aura that was not there. `/skuauratrace` was built
in the process and stays — it answers the real version of this question — but
the first check is cheaper: grep the SavedVariables for the aura's name.
